## Approved baseline and proposed boundary

Approved: independently administered organizations are tenants; branches sit within them; users may have separate memberships; organization and branch grants are explicit; capabilities deny by default without cross-organization privilege union. Phase 2C implements pure rules and trusted reader contracts, not authenticated callers or deployed isolation. Its `EvaluateActorDelegationScopeAsync` result verifies only actor scope: recipient existence, membership, status and actual grant execution remain unverified.

Recommend the first persistence slice be **synthetic read-only authorization adapters plus real-database isolation tests**. Runtime writes, administration, invitations, login/provider integration, public-product persistence, patient data and protected routes remain excluded. Test/setup tooling provisions synthetic states separately. The public DIN endpoint must remain usable without a database connection or identity service. Do not make its startup or health depend on this foundation database.

## Proposed schema

One shared PostgreSQL database, with `identity` and `organizations` schemas for module ownership. Schemas organize objects; they do not replace RLS. UUIDs are opaque references, not authorization tokens. All columns below are non-null unless stated; reject empty UUIDs. Use explicit checked text state/capability codes mapped to Domain enums, rather than depending on enum ordinals. Optional synthetic display labels are bounded text (proposed 160 characters), not identifiers or membership evidence.

| Table / owner | Minimal columns and keys | Constraints / purpose |
|---|---|---|
| `identity.staff_users` / Identity | `user_id uuid` PK, `is_enabled boolean` | Global application identity/status only. No name, email, password, provider token or patient attributes. External `(issuer, subject)` mapping is deferred until provider design; do not invent placeholder authentication. |
| `organizations.organizations` / Organizations | `organization_id uuid` PK, `status text`, `display_name text` | Status in active/suspended/closed. Shared branding never establishes tenancy. Label not unique. |
| `organizations.branches` / Organizations | PK `(organization_id, branch_id)`, `is_enabled boolean`, `display_name text` | FK organization to organization PK. Branch belongs to exactly one organization within this reference pair. No reassignment by update. Composite key supports deliberately overlapping branch references across synthetic tenants. |
| `organizations.memberships` / Organizations | PK `(organization_id, user_id)`, `status text`, `authorization_revision bigint` | FKs organization and global staff user; status active/suspended/removed; revision positive. Retain removed row as a tombstone so remove/recreate does not reset its revision. |
| `organizations.membership_branch_grants` / Organizations | PK `(organization_id, user_id, branch_id)` | Composite FK `(organization_id,user_id)` to membership and `(organization_id,branch_id)` to branch. A bare branch-ID FK is forbidden. Presence means explicit branch grant; no all-branches sentinel. |
| `organizations.capabilities` / Organizations | `capability_code text` PK | Migration-controlled catalogue: only `workspace.read` and `delegation.scope.evaluate`. No runtime insert/update. Codes explicitly map to `WorkspaceRead` / `DelegationScopeEvaluate`. |
| `organizations.membership_capabilities` / Organizations | PK `(organization_id,user_id,capability_code)`, `is_delegable boolean` | Composite membership FK and capability-code FK. Presence is a held capability. Proposed check permits `is_delegable=true` only for `workspace.read`; scope-evaluation authority cannot itself be delegated. Adapter maps true flags into the existing delegable-capability set. |

Use restrictive delete behavior for organizations, branches, users and memberships; no cascading purge or cross-organization transfer. Physical cross-module user FK is a proposed integrity dependency, not permission for Organizations to read Identity tables. Approve that lifecycle coupling under HUM-006; Identity deletion would require coordinated contracts, not a direct table purge.

PKs prevent duplicate memberships and grants. All tenant-owned uniqueness includes organization ID; do not make branch labels or tenant-local references globally unique. Index memberships `(user_id,organization_id)` for exact self lookup and possible later approved membership discovery; branch grants `(organization_id,branch_id,user_id)` for policy joins. Existing composite PK indexes cover most reader predicates; do not add low-selectivity status indexes without measurement. The membership-to-user FK is covered by the reverse membership index, and grant-to-branch FK by the reverse branch-grant index. The tiny immutable capability catalogue needs no extra deletion-maintenance index initially. Inspect query plans against synthetic data before claiming scale.

## Lifecycle, revisions and consistency

Disabled users, suspended/closed organizations, disabled branches and suspended/removed memberships must deny through the existing policy. Unknown stored states/capabilities must fail closed during materialization. No implicit reactivation or grants on user creation.

`authorization_revision` is an application revision, not PostgreSQL `xmin` and not a bearer credential. It advances on membership-state changes and changes to held/delegable capabilities or explicit branch grants. It never decreases or resets on reactivation. Multiple increments in one administrative transaction are acceptable; exact equality, not sequential counting, is the contract.

Propose database-owned triggers: membership updates control `OLD.revision + 1`; grant/capability row changes lock and bump the parent membership within the same transaction. Reject overflow and attempts to rewrite ownership or move grant rows between memberships. A dedicated trigger function would use a separate `revision_maintainer` NOLOGIN/NOBYPASSRLS owner with only the parent key/revision SELECT and revision-column UPDATE privileges plus explicit role-targeted RLS policies for that maintenance operation. Fully qualify objects, lock down `search_path`, revoke public execution and test its privilege surface. The exact parent comes from the changed trigger row, with no caller-supplied function arguments, tenant override, arbitrary SQL or authority to alter grants. Runtime cannot assume this role or call the function directly. This deliberate maintenance-policy exception must be reviewed alongside FORCE RLS; a table owner subject to FORCE RLS does not automatically have permission to seed/bump every row. Approve triggers versus an equally enforced constrained writer before implementation; runtime has no grant-writing privileges in the first slice.

User/organization/branch status is reread rather than represented solely by membership revision; disabling an organization must not require updating every membership. Start the authorization read transaction before either existing reader is called. A repeatable-read, read-only transaction gives one coherent snapshot for identity, organization, membership, grants and capabilities. A change committed before that transaction's snapshot must be observed. An in-flight snapshot can predate revocation; it cannot withdraw already delivered results. This is **not** an immediate global revocation or protected-write guarantee.

Later sensitive writes need separate approval: transactional revalidation/locking of relevant user, organization, branch and membership state, consistent lock order, optimistic revision predicates, required audit and conflict tests before commit. Do not assume a previously returned authorization context permits mutation.

## EF Core adapters and module boundaries

- `Identity.Infrastructure`: private EF entities/configuration and `IdentityDbContext`; implements existing `IStaffIdentityReader`, returning only `StaffIdentity(user_id,is_enabled)` for the validated actor. No provider behavior.
- `Organizations.Infrastructure`: private EF entities/configuration and `OrganizationsDbContext`; implements existing `IOrganizationAccessReader`, returning existing immutable Domain organization/branch/membership values and copied sets. Every query explicitly filters actor/organization and, for branch records, branch ID. No public entity or `DbContext` leaks into Application.
- Preserve `IStaffAuthorization`, `AccessRequest`, `AuthorizationContext`, `ActorDelegationScopeEvaluation` and Domain rules. Each module owns its mapped tables, migrations and configuration. Organizations has no Identity EF navigation, join or direct Identity table query; it consumes `IStaffIdentityReader`. Physical FK DDL is an explicitly reviewed exception to independently movable storage, not cross-module data access.
- A small shared Infrastructure connection/transaction primitive, with no module entities or permission rules, coordinates one scoped connection and transaction across both contexts. A composition-root Infrastructure decorator of `IStaffAuthorization` creates that scope, invokes the unchanged implementation, then disposes it. Readers refuse execution without the scope or with mismatched actor/tenant/branch. A base synthetic actor input comes from a test harness only; a future API must supply an authenticated principal through an approved flow.
- Share the same open connection and transaction explicitly between contexts; perform reader calls sequentially. Materialize results before returning them. Use no-tracking reads, short-lived contexts, no EF context pooling, lazy loading, parallel context operations, ambient mutable tenant singleton or deferred query escaping the transaction. Npgsql connection pooling is separate and remains enabled. [EF lifetime guidance](https://learn.microsoft.com/en-us/ef/core/dbcontext-configuration/) and [context-pooling guidance](https://learn.microsoft.com/en-us/ef/core/performance/advanced-performance-topics) support this distinction.

Do not register a production protected route or replace public DIN services. Only integration-test composition exercises these adapters initially. Future runtime wiring is a separate review gate.

## RLS strategy and the membership-bootstrap boundary

Application authorization and explicit query scoping remain mandatory. Recommend ENABLE and FORCE ROW LEVEL SECURITY on users and all tenant-owned tables, with command-specific policies. A tiny capability catalogue is non-sensitive shared metadata and needs only read grants. Schema ownership and migrations use separate credentials. [PostgreSQL RLS](https://www.postgresql.org/docs/18/ddl-rowsecurity.html) documents owner/privileged bypass and default denial; do not equate enabling RLS with complete isolation.

The bootstrap selector is not yet validated membership. The adapter may set a **candidate** organization/branch only inside a scope containing a trusted actor ID. A self-scoped membership read resolves whether that actor actually belongs there. Only after current identity, lifecycle, branch and capability/revision checks succeed does the Application result count as validated authority. There is no unrestricted preliminary membership query and no acceptance of a client organization ID as authority.

Proposed SELECT policy graph, deliberately avoiding recursive membership policies:

| Relation | Intended row visibility for the read role |
|---|---|
| Staff users | Exact current actor only; disabled state remains readable internally so the identity reader can deny. No global staff listing. |
| Memberships | Exact candidate organization plus current actor; this minimal self metadata can include inactive state. It does not query itself or require a fully authorized context first. |
| Branch grants / membership capabilities | Exact organization and actor, with current enabled self user and active self membership. Return the actor's own grants, not other staff memberships. |
| Organizations | Candidate organization plus enabled actor and active self membership. Suspended/closed state may remain visible internally for rejection. |
| Branches | Candidate organization AND exact candidate branch AND explicit self branch grant AND active self membership, enabled actor and active organization. Disabled branch state is available internally and rejected by Domain. |

Policy dependency direction is users/memberships -> grants/capabilities/organizations -> branches, with no membership-to-organization or self recursion. Reads of a user's own branch-grant references do not grant access to other branch records. Future tenant data policies must also require active organization and approved branch scope; the bootstrap metadata exception must never become a general data-read policy.

Fail closed on missing/empty context: a stable, invoker-rights context parser returns NULL for missing/invalid UUID settings, producing no matching row. Avoid errors containing supplied IDs; parameterize all settings and SQL. A guarded error is also denial, but tests must distinguish controlled rejection from successful queries. Verify malformed settings explicitly, not only valid UUIDs.

Initial runtime role is SELECT-only. No INSERT/UPDATE/DELETE policy or privilege exists for identity, memberships, grants or capability definitions. Future DML policies must define both USING (existing row) and WITH CHECK (new row), including unchanged tenant ownership and branch relationships; an EF filter alone cannot enforce that. Test-only branch DML probes described below exercise actual RLS write checks without introducing an application writer.

Roles proposed for approval:

- `platform_owner` NOLOGIN owns objects/policies and narrowly scoped trigger functions; not a runtime membership.
- Separate migration login may assume ownership for reviewed DDL only; never available to runtime or frontend. A distinct, tightly controlled `platform_provisioner` role has BYPASSRLS for synthetic seed/reset and privileged test setup. Give it only the fixture-table DML/schema USAGE needed for setup; BYPASSRLS itself does not supply those object privileges. That privilege is explicit, not implied by table ownership under FORCE RLS. No runtime or DML-probe role may inherit/assume it. Use a separate connection pool and short-lived setup credentials; never reuse provisioning connections for runtime assertions. A role that can alter/drop policies is also privileged.
- `platform_reader` LOGIN, NOSUPERUSER, NOBYPASSRLS, no ownership, CREATEROLE, CREATEDB, schema CREATE, DDL, TRUNCATE or membership in elevated roles. Only CONNECT, schema USAGE and specified SELECT grants. Revoke PUBLIC CREATE/excess function execution as appropriate; establish safe default privileges for future objects.
- Test-only RLS DML probe role has the same non-bypass attributes and controlled branch DML grants/policies. Its credentials and role membership never reach runtime. Backup/restore access is separately privileged, not borrowed from runtime.

**Threat limit:** custom PostgreSQL settings are writable session context, not authentication. An arbitrary-SQL attacker using runtime credentials may change actor/tenant settings, including impersonating an actor with membership. Membership predicates do not solve that. RLS here protects against missing/incorrect application predicates under a trusted context setter, not a fully compromised app/DB credential. Parameterization, least privilege and no public database access remain necessary; stronger independent identity binding/database-per-tenant needs a separate decision.

## Pooled connections and transaction-local context

For each authorization invocation, never per login session:

1. Validate input shape and obtain the trusted synthetic actor from test composition; no browser-supplied user identity. Open a connection from the read-role pool and start one explicit repeatable-read read-only transaction.
2. Before any protected SQL, parameterize `set_config('app.actor_id', actorText, true)`, `set_config('app.organization_id', candidateOrganizationText, true)` and `set_config('app.branch_id', candidateBranchText, true)` on that same transaction/connection. The third argument `true` is transaction-local. These are descriptive design examples, not executed SQL or a created schema.
3. Load only self-scoped metadata, verify membership and invoke existing authorization rules through the coordinated readers. Wrong actor/organization/branch/revision returns denial, not another tenant's details. Keep all reader queries inside this transaction, including retries of materialization if later approved.
4. Fully materialize immutable results. Commit a completed read transaction or roll back on denial/failure; in `finally`, end/dispose transaction before returning the connection. Cancellation uses bounded cleanup independent of an already-cancelled request token. On uncertain transaction/connection state, discard the broken connector rather than returning it as healthy.
5. Never use session-level SET, connection-startup tenant parameters, `No Reset On Close=true`, or tenant state in a shared data source/context. Keep Npgsql's default reset behavior; transaction locality is the primary boundary and reset is defense in depth. No PgBouncer/multiplexing in the first slice. No automatic retry strategy initially; any later retry must rebuild the whole scope, transaction and context, not replay a statement on an uninitialized connection.

[PostgreSQL SET](https://www.postgresql.org/docs/18/sql-set.html) explains commit/rollback and savepoint behavior; [configuration functions](https://www.postgresql.org/docs/18/functions-admin.html#FUNCTIONS-ADMIN-SET) explain `set_config`. Set context again if a future savepoint retry rolls back past it. Missing context must never fall back to a previously selected organization. Test transaction completion and real physical connection reuse, not just disposal of a logical object. [Npgsql connection parameters](https://www.npgsql.org/doc/connection-string-parameters.html) documents pool reset and pooling controls.

## Real PostgreSQL integration test plan: T-015

Planned only; no tests or database were created/run during planning. Use a dedicated persistence integration project, existing xUnit conventions and actual PostgreSQL of the approved version. No EF InMemory or SQLite substitute. Missing/unreachable database must fail the required CI job rather than silently skip. Provision/migrate/seed with isolated privileged setup credentials; all authorization assertions reconnect as the read role. Assert role flags, table owners, grants, policies and FORCE RLS before testing.

Fixtures: organizations A/B with the same branch reference values, A1/A2 branches, a multi-member user with different grants per organization, an A-only user, a disabled user, suspended organization/membership, removed membership, and exact capability/revision differences. No real staff identities or patient data. Parameterized queries and typed readers are both exercised.

| Planned case | Required evidence |
|---|---|
| Positive adapter mapping | Exact immutable Domain snapshot, all explicit self grants and correct capabilities/revision; two permitted branches and independent A/B access. |
| Missing/forged context | No actor/tenant/branch, invalid UUIDs, conflicting request/scope, user substitution, and no membership deny. Test arbitrary SQL changing actor context separately as a documented trust-limit demonstration, not a test expected to prove impossible impersonation. |
| Cross-tenant SELECT | Raw unscoped SQL under context A returns no B data; nested/aggregate/count/join paths and EF IgnoreQueryFilters cannot escape RLS; overlapping branch references cannot substitute ownership. |
| Branch restrictions | A1 grants do not expose A2 or B1; wrong branch-parent composite FKs fail even during privileged setup. No implicit organization-wide grants. |
| Lifecycle/revision | Disabled user/branch, suspended/closed organization, removed/suspended membership, unknown codes and stale/zero revision deny; a subsequent new transaction sees committed revocation, while B remains available if still authorized. Verify snapshot semantics with deterministic coordination, not timing sleeps. |
| Revision integrity | Direct setup changes to grants, delegable flags and membership state bump revisions atomically; no resets on remove/reactivate; rollback restores state/revision; attempted ownership transfer, overflow and privileged-function misuse fail. |
| Runtime writes | Read role cannot write any authorization table, execute privileged setup/trigger functions directly, alter/disable RLS, SET ROLE to owner, TRUNCATE or create a shadow policy function. Test errors without leaking another tenant's values. |
| Actual RLS writes | A separate test-only nonowner/NOBYPASSRLS role with branch DML privileges and USING/WITH CHECK policies demonstrates permitted same-scope label UPDATE and rejected cross-tenant INSERT/UPDATE/DELETE, tenant-key rewrites, branch substitution and missing context. Confirm the failure is RLS, not merely absent table privilege. Auth-control tables remain unwritable. No application grant/write API is inferred. |
| Pool contamination | Set max pool size one, capture backend PID, execute A then B then missing-context transactions on the same physical connection; test commit, rollback, cancellation, command failure and failed transaction recovery. No A data under B or unset context. Repeat independent concurrent scopes with separate checked-out connections and bounded waits. |
| Bypass risks | Verify actual read/probe roles are never owner/superuser/BYPASSRLS. Setup-only negative controls demonstrate privileged bypass; never report those controls as normal-runtime isolation passes. Check new table/default privilege coverage, raw SQL, views/functions and FK/unique error side channels. |
| Recovery/regression | Fresh database -> reviewed migrations -> synthetic seed -> tests; dump/restore to separate database -> role/RLS/fixture verification again. Existing 114 backend and 28 frontend cases remain green; public DIN remains independent of database outage. No claim about protected APIs that do not exist. |

## Migration, seed and restoration strategy

After approval only: create separate Identity/Organizations Infrastructure migrations and separate schema-qualified EF history tables, coordinated in deterministic order by an explicit local/test migration runner. Identity users precede organization membership FKs; roles/ownership are provisioned separately. Within each reviewed migration, create tables/constraints and RLS policies/grants together before runtime access. Include triggers, FORCE RLS and default privilege assertions in reviewed migration SQL; an EF-generated table model does not generate the whole security boundary. No `EnsureCreated`, automatic app-startup migration, runtime owner credential or runtime schema creation.

Review the generated SQL/bundle, bootstrap empty databases and test upgrade paths before applying anywhere else. Prefer forward fixes; destructive down-migrations, restoring over existing data or deleting volumes require explicit approval. [EF migration guidance](https://learn.microsoft.com/en-us/ef/core/managing-schemas/migrations/applying) recommends reviewing deployment SQL. No migration file or executable DDL is supplied in this planning task.

Seed capability codes as controlled migration reference data. Seed synthetic organization/user/membership fixtures only through an explicit nonproduction/test runner; deterministic references, bounded labels and known grants/revisions, no real emails/provider credentials/patient attributes. Setup is idempotent for its named fixture database, refuses non-test targets by explicit allowlist/marker and never auto-seeds production. Separate owner setup from runtime reads. No real-pharmacy onboarding or first-admin process is implied.

For a synthetic development database, propose a custom-format logical dump and restore into a **different** fresh database with matching roles/ownership and reviewed security schema. Do not use the tenant runtime role for whole-database backups: it can yield partial/denied views under RLS. Preserve/recreate role definitions and policies, then rerun isolation tests after restore. Protect even synthetic dump paths; never put credentials/dumps in Git. [PostgreSQL dump/restore guidance](https://www.postgresql.org/docs/18/backup-dump.html) describes privilege and ownership requirements. Production RPO/RTO, retention, encryption, offsite storage, WAL/PITR and tenant-specific recovery remain HUM-007/HUM-008 decisions, not implemented requirements. Shared-table backups imply shared restore scope; a tenant export is not a complete backup or approved tenant-restore procedure.
